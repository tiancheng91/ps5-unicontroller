# 版本发布

## 发布前

1. 确认准备发布的代码已提交并推送，包含工作流和 CHANGELOG 的更新。
2. 将 `CHANGELOG.md` 的 `Unreleased` 中已完成内容整理为对应版本章节，例如 `## [0.1.0] - 2026-11-14`；保留后续未发布修改。也支持 `[v0.1.0]` 标题。
3. 确认目标提交的 Actions 通过，并完成本次变更需要的 PS5 实机验证。CI 不证明设备或休眠兼容。

## 发布标签

在要发布的提交上执行，例如：

```sh
git tag -a v0.1.0 -m "Release v0.1.0"
git push origin v0.1.0
```

- `v0.1.0`：正式版。
- `v0.1.0-beta.1`、`v0.1.0-rc.1`：预览版（prerelease）。
- 标签必须是带 `v` 前缀的语义化版本，构建元数据如 `v0.1.0+build.1` 也可使用。
- 普通分支推送、Pull Request 和手动运行只构建测试产物，不发布 Release。手动运行标签工作流也不会发布。

项目默认不生成或推送标签。上面的命令是维护者主动发布的入口，不是安装步骤。

## 自动化流程

同一个构建任务依次执行格式检查、主机回归、浏览器回归、固定版本 SDK 下载校验和 PS5 交叉编译。全部成功后，标签推送才会进入独立的发布任务；仅发布任务授予 `contents: write`。

发布任务下载本次运行的产物，核验 ELF 校验和、版本、提交及远端标签仍指向该提交，然后上传：

- `unicontroller.elf`
- `unicontroller.elf.sha256`
- `build-info.txt`（版本、标签、提交、运行ID、Actions链接）

程序启动日志和 `/api/v1/system` 的版本也跟随标签，不依赖手动修改源码中的版本字符串。无标签构建使用 `dev`。本地主机与 PS5 构建均可用 `UC_BUILD_VERSION=0.1.0` 指定版本；切换版本参数前先 `make clean`，避免沿用旧目标。

若 CHANGELOG 有与标签精确匹配的非空版本章节，用该章节作为 Release 正文；没有对应章节时使用 GitHub 自动生成的说明，不把 `Unreleased` 当作某个版本的变更。重复或空的版本章节会报错。

## 失败与重试

先创建草稿，三个附件全部上传成功后才公开发布。发布失败时可重跑失败任务，继续完成草稿。已经公开的 Release 不会因重跑而覆盖附件；若需要修正，创建新的版本和标签，不移动已发布标签。

同一标签的发布任务串行执行。若标签在构建期间被移动，提交核验不通过。现有 Actions artifact 下载入口保留，便于未发布提交的验证。

本地解析、格式和流程静态检查不能证明 GitHub 实际发布成功；需要将工作流推送后，由一次真实版本标签运行验证。仓库或组织策略还必须允许 `GITHUB_TOKEN` 创建 Release。
